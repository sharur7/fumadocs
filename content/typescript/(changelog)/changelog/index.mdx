## Universal app mode by default

`APP_MODE` now defaults to `universal`. A server built with NitroStack serves widgets to both Claude and ChatGPT without any configuration: tools carry the metadata each host expects, and widget resources use the MCP Apps MIME type. Set `APP_MODE=openai` or `APP_MODE=mcp-app` only when you target a single host. See [Application mode](/docs/cli/configuration#application-mode-app_mode).

</Release>

## Transforms, data spillover, and two new templates

1.1.0 is about servers with a lot of tools and a lot of data. Transforms change which tools a client sees and how it calls them, data spillover keeps large results out of the model's context, and two new templates show both at work.

### Search and code-mode transforms

A [transform](/docs/sdk/transforms) sits between your tools and the client. The [search transform](/docs/sdk/transforms/search) replaces a long tool list with a search tool, using BM25 or regex matching, so the model discovers tools as it needs them. Without a query, it lists the catalog. The [code-mode transform](/docs/sdk/transforms/code-mode) lets the model write a short script that calls several tools in one step; scripts run in a QuickJS sandbox with memory limits. You can give both transforms custom tool descriptions.

### Data spillover

The [`DataSpilloverInterceptor`](/docs/sdk/data-spillover) catches tool results that are too large to send to a model. It returns a preview and a resource link, and stores the full result in memory or on the filesystem until the client reads it.

### Session-based tool visibility

Tools can be shown or hidden for each session through `ExecutionContext`, and clients are notified when the list changes. [Visibility](/docs/sdk/transforms/visibility) explains how to use it as a transform.

### New templates

`init` adds two templates: [Enterprise search](/docs/templates/enterprise-search), with finance, inventory, and support controllers behind the search transform, and [Code mode](/docs/templates/code-mode). Both include widgets built with Next.js.

### Improvements

- **Transports.** HTTP clients that don't accept `text/event-stream` get plain JSON responses.
- **Health checks.** The health resource includes transform pipeline and spillover metrics.
- **Pipeline.** Tools and decorators accept interceptor instances that are already configured.
- **Tools.** Synthetic tools accept arguments sent as a serialized JSON string.
- **Templates.** The new templates pin `@modelcontextprotocol/ext-apps` and `zod`, so installs stay on Zod 3.

### Fixes

- **Transforms.** A `CallToolResult` is no longer wrapped twice, and a `tools/call` that arrives before indexing finishes is handled.
- **Search.** Regex matching has a longer worker timeout and no longer leaks worker slots under load.

</Release>

## Python: a vendored SDK and a landing page

Projects created by `nitrostack-py init` now include their own copy of the SDK in `vendor/nitrostack`, added at `init` and refreshed by `pack`, so a deployed project carries exactly the SDK it was built with. `install` keeps using `uv sync` for everything else.

A Python server now answers `GET /` with a page that describes its MCP endpoint, like the TypeScript SDK.

### Fixes

- **HTTP.** A `GET /mcp` request that carries a session ID is rejected before an SSE stream opens.

</Release>

## Python SDK, rebuilt on its own MCP server

0.3.5 is the largest Python release so far. The SDK no longer builds on FastMCP: it runs its own low-level MCP server, which brings it level with the TypeScript SDK.

### MCP 2026-07-28

Python servers support the stateless 2026-07-28 revision of MCP. One `/mcp` endpoint serves both 2025 and 2026 clients, and the protocol era defaults to `auto`. In stateless mode, requests must carry the `Mcp-Method` header, and `tools/call` must also carry `Mcp-Name`; both must match the JSON-RPC body.

### What's new

- **Transports.** Streamable HTTP and legacy SSE, alongside STDIO.
- **Tasks.** The MCP tasks protocol, with a pluggable task store and per-tenant task authorization.
- **Auth.** OAuth 2.1, including Client ID Metadata Document resolution with SSRF protection.
- **Widgets.** Interactive widgets that talk to the host through bridge RPCs.
- **CLI.** `init` installs agent skills and creates the project's `.venv`, and templates use `uv`.

### Improvements

- **HTTP.** Servers bind to `127.0.0.1` by default, and trust a forwarded host only from trusted proxies.
- **Tools.** Tool schemas must use JSON Schema 2020-12; other drafts are rejected when the tool is registered.

</Release>

<Release date="7 Sep 2026" packages={[{ name: 'core', version: '1.0.16', lang: 'ts' }, { name: 'cli', version: '1.0.16', lang: 'ts' }]}>

## MCP 2026-07-28 and tasks

NitroStack servers support the stateless 2026-07-28 revision of MCP, and keep serving clients on the earlier revision. The default protocol era is `auto`.

### Tasks

Long-running tool calls can run as [tasks](/docs/sdk/tasks). Task storage is pluggable through a `TaskStore`, with an in-memory store by default. Tasks are authorized per tenant, cancelled tasks can't be updated, and only finished tasks expire. Status updates reach clients over SSE, the modern transport, or STDIO.

### Improvements

- **Auth.** A standard `OAuthGuard`, and stricter Client ID Metadata Document resolution: HTTPS only, no redirects, a 5 KiB response limit, a timeout, and protection against private network addresses.
- **Tools.** Input schemas allow additional properties, so contextual parameters don't fail validation.
- **Server.** Start options are configurable, and `PORT` takes priority when the HTTP port is resolved.

### Fixes

- **Transports.** The modern adapter answers `ping`, and passes an already parsed request body through, so Express JSON middleware works.
- **Widgets.** Widget metadata is kept when tools are registered, custom widget resource URIs work, and bundled widget files resolve by their clean filename.

</Release>

## Upgrade

<Tabs groupId="language" persist items={['TypeScript', 'Python']}>
<Tab value="TypeScript">

From your project folder, preview the changes, then apply them:

```bash
npx nitrostack-cli upgrade --dry-run
npx nitrostack-cli upgrade
```

`upgrade` updates the `@nitrostack/*` packages in your project and refreshes the agent skills. See [Manage Dependencies](/docs/cli/manage-dependencies#upgrade) for every option. To update a global install of the CLI, run `npm install -g @nitrostack/cli`.

</Tab>
<Tab value="Python">

```bash
pip install -U nitrostack
nitrostack-py upgrade --dry-run
nitrostack-py upgrade
```

In a project created by `init`, `upgrade` replaces the vendored copy of the SDK in `vendor/nitrostack` with the target release, downloading the wheel from PyPI and checking it against its published sha256. In other projects it updates the `nitrostack` entry in `pyproject.toml`, and `requirements.txt` when it already pins it; run `nitrostack-py install` afterwards. Use `--version X` to pick a release. A target older than the current version is rejected unless you pass `--allow-downgrade`. See [Manage Dependencies](/docs/cli/manage-dependencies#upgrade).

</Tab>
</Tabs>
